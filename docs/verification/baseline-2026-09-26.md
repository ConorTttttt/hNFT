## Current security/trust assumptions

### Unyt settlement

`initiate_transfer_from_rave` currently trusts caller-supplied:

- `fulfilled`
- `nft_id`
- `new_owner`
- `previous_owner`

The NFT zome does not independently fetch or verify the referenced RAVE.

The RAVE ActionHash is recorded in a link tag for audit/display, but is not itself settlement proof.

### NFT ownership

The caller must already be the current NFT owner according to the NFT provenance chain.

The payment bridge therefore does not bypass the existing ownership check.

### NFT/Unyt identity

The integration assumes:

    nft_id == ActionHash.to_string()

It also assumes Unyt owner strings correspond to `AgentPubKey::to_string()`.

These are application-level conventions, not independently verified cross-DNA identities.

### max_supply

When `minter_pubkey` is configured and `max_supply > 0`, mint validation counts prior NFT manifest creates on the minter's ordered source chain.

When `minter_pubkey` is absent, the collection operates in open/dev minting mode and the cap is not enforced.

### Blind-box resolution

The minter performs blind assignment resolution. The current design therefore retains the documented minter-trust/fairness concern.

Resolution currently creates the assignment and a transfer commitment to the buyer.

### Recovery / atomicity

Payment settlement and NFT transfer remain separate operations.

There is no demonstrated atomic NFT-for-payment transaction across the two DNAs.

Blind-purchase recovery/refund/dispute handling remains an identified gap.

### Sale escrow

The baseline retains the previously identified concern that the NFT zome does not independently establish Unyt escrow uniqueness and seller ownership from the settlement record.
